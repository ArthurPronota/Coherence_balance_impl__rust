# Coherence и балансировка реализаций в Rust

## Что такое coherence

**Coherence** (когерентность) — свойство системы трейтов, при котором для **каждой пары** `(type, trait)` существует **не более одной** реализации, **видимой** во **всей** программе.

**Формально:**

> Для любого типа `T` и трейта `Tr` может быть **не более одной** реализации `impl Tr for T` в **итоговом** бинарнике.

## Зачем нужна coherence

### Проблема **без** coherence

Представьте, что **две** библиотеки реализуют **один** trait для **одного** типа:

```rust
// Библиотека A
impl Display for Vec<i32> {
    fn fmt(&self, f) -> ... {
        write!(f, "A: {:?}", self)
    }
}

// Библиотека B
impl Display for Vec<i32> {
    fn fmt(&self, f) -> ... {
        write!(f, "B: {:?}", self)
    }
}
```

**Что произойдёт при вызове?**

```rust
let v = vec![1, 2, 3];
println!("{}", v);   // "A: [1, 2, 3]" или "B: [1, 2, 3]"?
```

**Компилятор не может выбрать** — **неоднозначность** → **непредсказуемое** поведение.

**Coherence** **запрещает** такие ситуации.

## Как coherence поддерживается

### 1. **Orphan Rule**

Реализовать trait можно, если **trait** или **type** — **в текущем** крейте:

| Trait в моём крейте | Type в моём крейте | Разрешено? |
|---|---|---|
| ✅ | ✅ | ✅ |
| ✅ | ❌ | ✅ |
| ❌ | ✅ | ✅ |
| ❌ | ❌ | ❌ |

**См. ответ про orphan rule.**

### 2. **Запрет перекрывающихся реализаций**

Даже если **orphan rule** соблюдён, **нельзя** иметь **две** реализации для **одного** типа:

```rust
impl<T> Foo for T { }   // ← реализация для ВСЕХ T

impl Foo for i32 { }    // ❌ ошибка: conflict
```

**Ошибка:**

```
error[E0119]: conflicting implementations of trait `Foo` for type `i32`
 --> src/main.rs:5:1
  |
5 | impl Foo for i32 {
  | ^^^^^^^^^^^^^^^^ conflicting implementation for `i32`
```

### Почему

- **`impl<T> Foo for T`** — покрывает **все** типы, включая `i32`.
- **`impl Foo for i32`** — **дублирует** `i32`.
- **Две** реализации для `i32` → **неоднозначность** → **запрещено**.

## Разбор вашего примера

```rust
trait Foo { }

// Реализация-покрытие (blanket implementation)
impl<T> Foo for T { }

// ❌ Конфликт
// impl Foo for i32 { }
```

### Blanket implementation

```rust
impl<T> Foo for T { }
```

**Читается:** «Реализуй `Foo` для **любого** типа `T`».

**Используется** в стандартной библиотеке:

```rust
// Все типы, реализующие Display, реализуют ToString
impl<T: Display> ToString for T { }
```

### Почему `impl Foo for i32` **нельзя**

**`impl<T> Foo for T`** уже **покрывает** `i32`. Вторая реализация — **конфликт**.

**Исключение:** если первая реализация **ограничена**:

```rust
impl<T: Display> Foo for T { }   // только Display-типы

impl Foo for MyType { }          // MyType не Display — OK
```

**Правило:** компилятор **проверяет**, что реализации **не пересекаются**.

## Coherence и orphan rule — **разное**

| | Orphan Rule | Coherence |
|---|---|---|
| **Что** | Где можно реализовать | Сколько реализаций |
| **Ограничение** | Trait/type в текущем крейте | Одна реализация на пару |
| **Пример** | `impl Display for Vec<i32>` — ❌ | `impl Foo for i32` дважды — ❌ |
| **Цель** | Предсказуемость | Однозначность |

**Coherence** — **более широкое** понятие. **Orphan rule** — **один из** механизмов.

## Балансировка реализаций

### Проблема

**Orphan rule** **ограничивает** **потребителей** (downstream):

```rust
// Мой крейт
// Хочу реализовать Display для Vec<i32> — ❌ orphan rule
```

**Владельцы** (upstream) — **trait** или **type** — **решают**, что можно:

```rust
// std
impl Display for Vec<i32> { }   // ← только std может
```

**Потребители** **не могут** добавить **свою** реализацию.

### Что такое балансировка

**Балансировка реализаций** — **пересмотр** orphan rule с целью **сместить баланс** между **upstream** (владельцы) и **downstream** (потребители).

**Идея:** позволить **downstream** реализовать **чужой** trait для **чужого** типа, **но** с **явным** указанием.

### Пример

**Сейчас:**

```rust
impl Display for Vec<i32> { }   // ❌ orphan rule
```

**С балансировкой** (гипотетически):

```rust
impl Display for Vec<i32> 
where
    use ThisCrate,   // ← явное указание
{ }
```

**Требует** от пользователя **явно** указать, **какую** реализацию использовать, если компилятор **не может** вывести.

### Почему **пока нет**

- **Сложность** — нужно **убедиться**, что нет **конфликтов**.
- **Обратная совместимость** — старые реализации могут **сломаться**.
- **Ясность** — пользователь **должен** понимать, **что** происходит.

## Как **обходим** ограничения **сегодня**

### Newtype Pattern

```rust
// ❌ Нельзя
// impl Display for Vec<i32> { }

// ✅ Обход через newtype
struct MyVec(Vec<i32>);

impl Display for MyVec {
    fn fmt(&self, f) -> ... {
        write!(f, "{:?}", self.0)
    }
}
```

**Плюсы:**

- **Работает**.
- **Типобезопасно**.

**Минусы:**

- **Дополнительный** тип.
- **Нужны** преобразования (`MyVec(v)` / `v.0`).
- **«Костыль»**.

### Другие обходы

- **`Wrapper`** из `serde_with`.
- **Локальный trait** + blanket impl.
- **Макросы** для генерации обёрток.

| | Coherence | Orphan Rule |
|---|---|---|
| **Что** | Одна реализация на (trait, type) | Где можно реализовать |
| **Уровень** | Система трейтов | Правило |
| **Механизм** | Запрет перекрытий | Trait/type в крейте |
| **Цель** | Однозначность | Предсказуемость |

## Сводная таблица балансировки

| Аспект | Сейчас | Балансировка (гипотетически) |
|---|---|---|
| **Downstream может** | Только свои traits | Чужие traits с `use` |
| **Орфан-правило** | Строгое | Ослабленное |
| **Обход** | Newtype | Прямая реализация |
| **Сложность** | Простая | Высокая |
| **Статус** | Работает | Не реализовано |

## Итог

- **Coherence** — свойство системы трейтов: **одна** реализация на пару `(type, trait)`.
- **Зачем** — **предсказуемость** и **однозначность**.
- **Поддерживается:**
  - **orphan rule**;
  - **запретом перекрытий**.
- **Blanket implementation** (`impl<T> Foo for T`) — **покрывает** все типы.
- **`impl Foo for i32`** после blanket — **конфликт**.
- **Orphan rule** и **coherence** — **разные**, но **связанные** понятия.
- **Балансировка реализаций** — **пересмотр** orphan rule с **явным** указанием.
- **Пока не реализована** — **обходим** через **newtype**.
- **Newtype** — **«костыль»**: работает, но **дополнительный** тип.
- **Правило:** coherence **гарантирует** одну реализацию; orphan rule **ограничивает** где.
